### 浏览器缓存位置

浏览器中的缓存位置（优先级从高到低）：

1. Service Worker
2. Memory Cache（内存缓存）
3. Disk Cache（硬盘缓存）
4. Push Cache（HTTP/2）

![[Pasted image 20250613230902.png]]

#### Service Worker

**Service Worker 的缓存与浏览器其他内建的缓存机制不同，可以自由控制缓存哪些文件、如何匹配缓存、如何读取缓存，并且缓存是持续性的。**

参见 [[Service Worker 缓存]]


当 Service Worker 没有命中缓存的时候，就调用 `fetch` 函数获取数据。也就是说，如果没有在 Service Worker 命中缓存的话，会根据缓存优先级去查找数据。**但是不管我们是从 Memory Cache 中还是从网络请求中获取的数据，浏览器都会显示我们是从 Service Worker 中获取的内容。**

#### Memory Cache

Memory Cache 也就是内存中的缓存：
- 读取内存中的数据比硬盘快的多
- 缓存持续性很短，会随着进程的释放而释放，一旦我们关闭 Tab 页面，内存中的缓存也就被释放
- 计算机内存小，不能去缓存太多内容

缓存规则：
- Memory Cache **在缓存资源时并不关心返回资源的 HTTP 缓存头 Cache-Control 是什么值，同时资源的匹配也并非仅仅是对 URL 做匹配，还可能会对 Content-Type，CORS 等其他特征做校验**。
- 虽然内存中可以存储大部分的文件，比如说 JSS、HTML、CSS、图片等等。但是浏览器会把哪些文件丢进内存则完全是由浏览器来适时决定的，不能被控制。
	- 当前中页面中已经抓取到的资源，例如页面上已经下载的样式、脚本、图片等，大概率会先放到内存缓存
	- 对于大文件来说，大概率是不存储在内存中的，反之优先
	- 当前系统内存使用率高的话，文件优先存储进硬盘

#### Disk Cache

Disk Cache 是硬盘中的缓存，读取速度慢点，但是 容量大、存储时效长，所以使用的也最多。

缓存规则：（这个是我们后面的缓存指令和策略可以控制的）
它会根据 HTTP Herder 中的字段判断哪些资源需要缓存，哪些资源可以不请求直接使用，哪些资源已经过期需要重新请求。**并且即使在跨站点的情况下，相同地址的资源一旦被硬盘缓存下来，就不会再次去请求数据。**

#### Push Cache

Push Cache (推送缓存）是 HTTP/2 中的内容：
- 缓存时间短暂，只在会话（Session）中存在，一旦会话结束就被释放，在 Chrome 浏览器中只有 5 分钟左右
- 并非严格执行 HTTP 头中的缓存指令

特点
- 所有的资源都能被推送，但是 Edge 和 Safari 浏览器兼容性不怎么好
- 甚至可以推送 `no-cache` 和 `no-store` 的资源
- 一旦连接被关闭，Push Cache 就被释放
- Push Cache 中的缓存只能被使用一次
- 浏览器可以拒绝接受已经存在的资源推送
- 可以给其他域名推送资源
- 多个页面可以使用相同的 HTTP/2 连接，也就可以使用同一个 Push Cache。这主要还是依赖浏览器的实现而定，出于对性能的考虑，有的浏览器会对相同域名但不同的 tab 标签使用同一个 HTTP 连接。

### 浏览器缓存策略 ⭐️

浏览器缓存策略主要分为两种：强缓存和协商缓存。都要配合 HTTP 的缓存首部使用。会先后判断使用。

#### 强缓存

- 不需要向服务器发送请求，直接使用本地缓存
- 通过 HTTP 响应头控制：
	- Cache-Control：滑动时间戳
		- max-age=N：缓存有效时间（秒）
			- max-age=0：缓存立即过期（因此会去服务器协商验证资源有效）
		- **no-cache：不直接使用缓存（即使未过期），需要去服务器协商验证资源有效**
		- **no-store：完全禁用缓存存储**
		- private：仅浏览器可缓存
		- public：中间代理/CDN 等也可缓存
		- 注意⚠️：max-age=0 和 no-cache 语义不同，但实际效果一致。推荐语义化更好的 no-cache
	- Expires：绝对过期时间点（已被 Cache-Control 取代）

#### 协商缓存

- 需要**向服务器发送请求，验证资源是否有效**。如果有效会返回 **304**，表示可以使用本地缓存
- 方式一：基于文件修改时间。由于使用的是绝对时间，如果服务端和客户端系统时间不一致就会出现误差
	- 响应头 Last-Modified
	- 请求头 If-Modified-Since
- 方式二：基于文件哈希。文件生成哈希值需要做运算，如果文件很多很大，得不偿失
	- 响应头 ETag
	- 请求头 If-None-Match

> 两种方式各有优劣,看业务而定

#### 启发式缓存

- 如果服务器未明确指定缓存头，浏览器可能会自行推断缓存行为
- 规则：计算资源的 `Last-Modified` 与当前时间 Date 的差值，按一定比例（如 10%）设置缓存时间。
- 例如：若资源 10 天前修改，可能缓存 `1 天`（10% × 10 天）。
- 注意事项：永远不要依赖启发式缓存，请显式设置缓存策略

#### 最佳实践 ⭐️

- 带版本控制的文件文件，如 CSS、JS 代码文件，打包会有 hash 标识
	- 策略：使用长期强缓存，由于文件名会带 hash，所以更新后不会走缓存，可以放心设置
	- 代码：`Cache-Control: public, max-age=31536000  # 缓存1年`
- 文件名固定，且长期不变的资源文件，如图片、CDN 资源
	- 策略：使用短期强缓存
	- 代码：`Cache-Control: public, max-age=604800  # 缓存7天`
- HTML 文件
	- 策略：使用协商缓存，每次都去服务器验证，保证页面能正常刷新
	- 代码：`Cache-Control: no-cache`, 服务器配合设置 `ETag` 或者 `Last-Modified`
- API 请求
	- 视业务需求而定
- 开发环境
	- 策略：完全禁用缓存，防止开发代码有缓存
	- 代码：`Cache-Control: no-store`
- 长效缓存
    - immutable: 比如 cdn 资源如果想永久不刷, `Cache-Control: public, immutable`
