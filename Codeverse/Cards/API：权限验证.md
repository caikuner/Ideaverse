## 如何做项目中的权限控制

目前我们的项目主要都是用的基于角色的访问控制（RBAC）：

- 权限列表
  权限标识：`模块.操作`
  角色：拥有一组权限，比如 `app.write`,`dict.read`
  用户：分配角色，支持多个
- 用户登录
  - 用户完成登录后，用户中心会去向 MPS 平台 (百度内部权限管理平台) 请求该用户对本系统的权限列表 permissions，并在上下文中赋给当前 user
  - 于是，每个用户就有了一组权限标识 `permissions:['app.write', 'dict.read']`

验证

- 后端：中间件验证请求，校验 permissions 是否有所需标识
- 前端：菜单/路由/按钮设置权限，hasPermission 工具函数根据其所属的模块，计算当前操作所需要的最小权限标识（为方便计算，统一计算成数值），验证 permissions 是否具有

## 访问控制模型 RBAC vs ABAC

### RBAC (基于角色的访问控制, Role-Based Access Control)

**核心概念**:

- 权限分配给角色而非直接给用户
- 用户通过成为角色成员获得权限
- " 角色 " 作为用户和权限之间的中介层

**主要特点**:

- 简单易管理，适合组织结构明确的场景
- 权限变更只需调整角色分配
- 典型的 " 最小权限 " 原则实现方式
- 广泛应用于企业系统和操作系统中

**示例**:

- " 管理员 " 角色拥有所有权限
- " 财务人员 " 角色只能访问财务系统
- " 普通用户 " 角色只有基本权限

### ABAC (基于属性的访问控制, Attribute-Based Access Control)

**核心概念**:

- 基于属性 (用户、资源、环境等) 动态评估访问权限
- 使用策略规则定义访问条件
- 更细粒度的访问控制

**主要特点**:

- 高度灵活，支持复杂条件
- 可考虑多种因素 (时间、位置、设备状态等)
- 适合云计算、IoT 等动态环境
- 实现相对复杂，需要策略引擎

**示例**:

- " 只有部门经理在工作时间才能访问敏感文件 "
- " 来自公司内部网络的设备可以访问研发服务器 "
- " 交易金额超过 $10,000 需要二级审批 "

### 对比总结

| 特性       | RBAC                   | ABAC                   |
| ---------- | ---------------------- | ---------------------- |
| 控制粒度   | 中等 (基于角色)        | 精细 (基于多种属性)    |
| 管理复杂度 | 较低                   | 较高                   |
| 动态性     | 静态 (角色变更才调整)  | 动态 (实时评估)        |
| 适用场景   | 组织结构固定的传统系统 | 云计算、IoT 等动态环境 |
| 策略表达力 | 有限                   | 强大                   |
| 实现难度   | 简单                   | 复杂                   |

现代系统常结合使用两者，在 RBAC 基础上增加 ABAC 特性实现更灵活的访问控制。
