> 面试题：前端路由原理？两种实现方式有什么区别？

### 路由和前端路由

**路由**（**routing**）就是通过互联的 [网络](https://zh.wikipedia.org/wiki/%E4%BA%92%E8%81%AF%E7%B6%B2) 把 [信息](https://zh.wikipedia.org/wiki/%E4%BF%A1%E6%81%AF) 从源地址传输到目的地址的活动，发生在 [OSI网络参考模型中](https://zh.wikipedia.org/wiki/OSI%E6%A8%A1%E5%9E%8B) 的第三层即 [网络层](https://zh.wikipedia.org/wiki/%E7%BD%91%E7%BB%9C%E5%B1%82)。

路由器有两种机制：

路由 -> 决定数据包从来源到目的地的路径。

转发 -> 将输入端的数据转移到合适的输出端。

早期的网站是后端路由 (比如 php 开发)：

- 服务器渲染生成好 HTML，每个页面有自己对应的 URL。
- 前端浏览时，URL 发送到服务器，服务器正则匹配，交给 Controller 进行相应处理
- Controller 拿到相应数据，加载 js css 渲染生成好 HTML, 把文件直接交给前端去显示
- SEO 好，但是各种 HTML 数据和路由逻辑混杂，且都要交给后端维护

之后的前端路由可以分为两个阶段：

1. 前后端分离阶段（比如 jQuery 开发）：

Ajax 的出现带来了前后端分离，后端提供 API，前端 Ajax 获取数据来展示。路由逻辑可以前端自己来定，每个 URL，需要什么数据自己拿就好了。

1. 前端单页路由阶段（vue react angular）:

在前后端分离的基础上，前端只有一个单页入口，自己加一套前端路由规则，比以往更好维护。

### 前端路由原理

前端路由 `route` 是指根据 url 分配到对应的处理程序，原理和路由器原理相似：

不同的请求地址, 会交给路由处理来转发给相应的控制器处理，所以路由就可以在转发前修改转发地址。

前端路由主要实现了两个功能（使用 ajax 更新页面状态的情况下）：

1. 记录当前页面的状态（保存或分享当前页的 url，再次打开该 url 时，网页还是保存（分享）时的状态）
2. 可以使用浏览器的前进后退功能（如点击后退按钮，可以使页面回到使用 ajax 更新页面之前的状态，url 也回到之前的状态）

作为开发者，要实现这两个功能，我们需要做到：

1. 改变 url 且不让浏览器向服务器发出请求；
2. 监测 url 的变化；
3. 截获 url 地址，并解析出需要的信息来匹配路由规则。

前端路由实现起来其实很简单，本质就是**监听 URL 的变化**，然后匹配路由规则，显示相应的页面，并且无须刷新页面。目前前端使用的路由就有两种实现方式

- Hash 模式
- History 模式

### Hash 模式

**hash 模式是使用** **URL 的 hash** **来模拟一个完整的 URL。通过锚点值的改变，根据不同的值，渲染指定 DOM 位置的不同数据。**

在浏览器中符号 # 以及#后面的字符称之为 hash，用 window.location.hash 读取。hash（#）是 URL 的锚点，代表的是网页中的一个位置，单单改变#后的部分，浏览器只会滚动到相应位置，不会重新加载网页。

**也就是说，hash 虽然出现在 URL 中，不会被包含在 http 请求中，因此改变 URL（hash） 不会再次向后端发起请求，也就\*\***不会重新加载页面\***\*。**

`www.test.com/#/` 就是 Hash URL，当 `#` 后面的哈希值发生变化时，可以通过 `hashchange` 事件来监听到 URL 的变化，从而进行跳转页面，并且无论哈希值如何变化，服务端接收到的 URL 请求永远是 `www.test.com`。

hash 模式背后的原理就是 **onhashchange** 事件 (监测 hash 值变化)，可以在 window 对象上监听这个事件。hash 改变会触发 hashchange 事件，浏览器的进后退也能对其进行控制，所以在 html5 的 history 出现前，基本都是使用 hash 来实现前端路由的。

```
window.addEventListener('hashchange', () => {
  // ... 具体逻辑
})
```

Hash 模式相对来说更简单，并且兼容性也更好。

### History 模式

History 是 HTML5 推出的 API，使用原理总结如下：

- 使用 `back、forward、go` 来切换状态
- 一旦有上面三个切换或浏览器动作，就会触发 `window.popstate` 事件，也就是说这个事件提供了对 路由切换的拦截
- 使用 `history.pushState` 和 `history.replaceState` 修改历史状态 (改变 URL)

（1）切换历史状态 (back、forward、go 三个方法，对应浏览器的前进，后退，跳转操作)

history.go(-2); //后退两次

history.go(2); //前进两次

history.go(0)  // 刷新

history.back(); //后退

hsitory.forward(); //前进

（2）修改历史状态

    包括 `pushState`、`replaceState` 两个方法，这两个方法接收三个参数：`stateObj，title，url` 。

用于向浏览器历史记录栈添加和修改条目。

使用 history.pushState() 方法时，就是将新生成的 url（记录）进行一次 `入栈` ，使其在栈顶。

使用 history.replaceState() 方法时，并不产生新记录，是修改当前栈顶的历史记录。

**当它们执行修改时，虽然改变了当前的 URL ，但只会更新浏览器的历史记录，浏览器不会立即向后端发送请求，因而也不会引起页面的重新刷新，只是进行了历史记录的切换。**

stateObj 对象 可以保存任意类型的数据,以保存历史页面的各种状态。比如，页面字体颜色、滚动跳位置、阅读进度、音乐播放器进度，都可以存储到 stateObj 中，后面再切换回这条记录时，通过 **event.state** 取到这个 state 对象，从而可以对页面状态进行高度还原。

```
// 新增历史记录
history.pushState(stateObject, title, URL)
// 替换当前历史记录，但注意，替换后，原页面后面的记录就都没了
history.replaceState(stateObject, title, URL)
```

（3）popstate 实现 history 路由拦截，监听页面返回事件

　　当 (浏览器动作或 api 切换) 活动历史记录条目更改时，将触发 popstate 事件。

- 只有在做出浏览器动作或者调用 history.back 三个 api 时，才会触发该事件
- 调用  history.pushState()  或  history.replaceState()  用来在浏览历史中添加或修改记录，不会触发 popstate 事件
- 如果被激活的历史记录条目是通过对  history.pushState()  的调用创建的，或者受到对  history.replaceState()  的调用的影响，popstate 事件的 state 属性包含历史条目的状态对象的副本，也是可以通过 e.state 获取。

```
window.addEventListener('popstate', e => {
  // e.state 就是 pushState(stateObject) 中的 stateObject
  console.log(e.state)
})
```

- 小结

```
window.history.pushState(state, title, url)
// state：需要保存的数据，这个数据在触发popstate事件时，可以在event.state里获取
// title：标题，基本没用，一般传 null
// url：设定新的历史记录的 url。新的 url 与当前 url 的 origin 必须是一样的，否则会抛出错误。
//      url可以是绝对路径，也可以是相对路径。
//如 当前url是 https://www.baidu.com/a/,执行history.pushState(null, null, './qq/')，则变成 https://www.baidu.com/a/qq/，
//执行history.pushState(null, null, '/qq/')，则变成 https://www.baidu.com/qq/

window.history.replaceState(state, title, url)
// 与 pushState 基本相同，但它是修改当前历史记录，而 pushState 是创建新的历史记录


window.addEventListener("popstate", function(e) {
    // 监听浏览器前进后退事件，pushState 与 replaceState 方法不会触发
  const state = e.state;
});
window.history.back() // 后退
window.history.forward() // 前进
window.history.go(1)  // 前进一步，2为前进两步，window.history.lengthk可以查看当前历史堆栈中页面的数量
window.history.go(-1) // 后退一步，-2为后退两步
```

【注意】

在当前流行的单页面应用中，**hash 模式下，前端路由修改的是#中的信息，而 http 请求时不会带着 hash，所以不会出现问题**。

但是在 history 下，个人拥有完全的自由去修改 path，它不怕前进和后退，因为记录了。但是怕刷新，**当刷新时，如果服务器中没有相应的响应或者资源，就会返回 404，因为刷新是实实在在地去请求服务器的**。

所以 history 路由需要服务端的支持，要在服务端增加一个覆盖所有情况的候选资源：如果 URL 匹配不到任何静态资源，则应该返回同一个 `index.html` 页面（将所有的路由重定向到根页面），不然就会到 404 页面。

### 两种模式对比

Q: 已经有 hash 模式了，而且 hash 能兼容到 IE8， history 只能兼容到 IE10，为什么还要搞个 history 呢？

- Hash 本来是拿来做页面定位的，如果拿来做路由的话，原来的锚点功能就不能用了。
- Hash 模式的**传参是基于 url 的**，只能更改哈希值，也就是字符串 ，如果要传递复杂的数据，会有体积的限制。而 history 模式不仅可以在 URL 里放参数，还可以可以通过 API 添加任意类型的数据到历史记录 (stateObj) 中。
- hashchange 事件，只可以更改 `#` 后面的内容，而 History API 可以设置任意的同源 URL
- 当使用 history 模式时，URL 就像正常的 url，不会像 hash 有一个 # ，更加的美观。
- Hash 模式的优点则是无需后端配置，并且兼容性好。History 模式在用户手动输入地址或者刷新页面的时候会发起 URL 请求，后端需要配置 `index.html` 页面用于匹配不到静态资源的时候
