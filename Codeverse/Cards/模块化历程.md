> 涉及面试题：为什么要使用模块化？都有哪几种方式可以实现模块化，各有什么特点？

## 为什么要模块化

在前端开发早期，js 作为一种脚本语言，只是做一些简单的表单验证和动画实现，代码量比较少。

随着 ajax 异步请求的出现，慢慢开始形成前后端分离，到了今天：客户端承载的代码量和业务量越来越多，许多服务端的代码也转移过来。程序代码越写越多，在一个文件里代码越来越长，越来越难以维护。

为了应对代码量的激增，编写可维护的代码，我们就希望能有一种方式，把代码组织在多个 js 文件中，进行维护，提高可读性和可维护性。

与模块化紧密相关：

- Node : Node 采用 CommonJS 规范导入导出模块
- npm 分发：npm 分发模块、包
- 模块打包工具 webpack/rollup
- ESM 原生模块化方案

使用模块化可以给我们带来以下好处：

- 提高代码可维护性：代码组织在一个个模块中，可读性和可维护性都更好
- 解决函数、变量命名冲突：不同的模块享有不同的环境，相同名字的函数和变量可以分别存在不同的模块中，完全不必考虑名字在模块之间冲突。
- 提供复用性：当一个模块编写完毕，就可以被其他地方引用。我们在编写程序的时候，也经常引用其他模块，比如 Node 内置的模块和来自第三方的模块

## 模块化解决方案

模块化发展的过程也是很长的，早期主要使用函数作用域来隔离，现在使用模块加载器，未来原生的 ESM 规范兼容良好后，就不需要借助 webpack 等工具了。

1. 使用函数封装
   最开始就是借助于函数作用域的隔离作用，把代码封装在一个个函数中。
   缺点：函数名全局污染

2. 命名空间（namespace）
   模拟类提供私有和共有方法来实现模块化，减少了 global 中的变量
   缺点：本质上就是对象，私有成员会暴露出去，内部状态可以被外部改写，一点不安全

```
var namespace = {
  methodOne: function () { /* ...*/ },
  methodTwo: function () { /* ...*/ }
}
namespace.methodOne()
```

3.使用匿名闭包的立即执行函数 ⭐立即函数调用表达式 ( IIFE)
使用立即执行函数实现模块化是比较常用的手段，也是通过函数作用域解决了命名冲突、污染全局作用域的问题。

缺点：1.只有知道每一个模块返回对象的命名才能使用2.代码混乱，每个文件代码都要包裹在一个匿名函数中3.没有统一规范

```
(function(globalVariable){
   globalVariable.test = function() {}
   // ... 声明各种变量、函数都不会污染全局作用域
})(globalVariable)
```

4.module loader 🎈

CommonJS AMD  CMD(废弃) ESM

使用 namespace 和匿名闭包都是以对象为单位，而不是文件为单位。依然难以解决依赖的问题。
CommonJS，规定文件即模块 - 于是在全局和私有作用域之外，人为出现一个以 `文件` 划分的作用域：在文件（即模块）中定义的成员将为 `文件私有`。再以文件即模块为单位导出和引入，就变得方便起来。
但同步的 CommonJS 规范最初提出来是用于浏览器以外的地方，当时被命名为 ServerJS，后来为了体现它的广泛性，修改为 CommonJS，Node 是 CommonJS 在服务端一个具有代表性的实现。之后相继出现了适用于浏览器的异步 AMD、通用模块定义 CMD（已经废弃）、旨在统一解决服务器和浏览器的 ES6 Module 等方案，以及后来的 Webpack、Rollup 等模块打包工具。

下面就来介绍这四种模块加载规范。

## **同步 CommonJS**

CommonJS 用同步的方式加载模块。在服务端 Node 环境下，模块文件都存在本地磁盘，I/O 读取非常快，所以这样做不会有问题。但是在浏览器端，限于网络原因，更合理的方案是使用异步加载方案。

Node 中实现 commonJS 的本质就是对象的引用赋值，module.exports exports require 的对象 三个默认指向的是同一块地址。

- 规定每个.js 文件都是一个模块，它们内部各自使用的变量名和函数名都互不冲突
- 有四个重要的环境变量为模块化的实现提供支持：`module`、`exports`、`require`、`global`。

### 导入

用 `require` 加载模块，引入的对象具体是什么，取决于引入模块输出的对象。

在导入使用时，导入的一直是 `module.exports` 的内容，而不一定是 exports 的内容。

```
module.exports = {
    foo: function () { return 'foo'; }
};

module.exports = function () { return 'foo'; };
```

### 导出

实际使用时，用 `module.exports` 定义当前模块对外输出的接口，输出的变量可以是任意对象、函数、数组等。

`exports` **不是变量，只是** `module.exports`**的赋值引用**，这**两个对象指向同一块内存**。

module.exports 和 exports 一开始都是一个空对象 { }，对属性的更改可以同步添加到两者。也就是说 module.exports 和 exports 是等价的 **（前提是：不去改变它们指向的内存地址）**

- 对 module.exports 的重写会挂载到 module.exports，而不是 exports
  对 module.exports 的重写改变了其内存地址，两者不再指向同一内存，module.exports 与 exports 不再等价。
- 同理，对 exports 重写（直接赋值) 会改变内存地址，二者不再共享内存。那 exports 的变化反映不到 module.exports 上。 在导出时的表现就是 module.exports !== exports。但是在导入使用时，**导入的一直是 module.exports** , 就会出现与 exports 内容不一致的错误。
- 所以推荐**一律直接使用 module.exports 导出**，而不是使用 exports，exports 更不能直接赋值修改。

CommonJS 模块输出的是**值的缓存（拷贝），不存在动态更新**。

- 如果导出基本类型，作为值的复制，导入后当然不会共享
- 如果导出引用类型，作为引用值的复制，导入后是可以共享变化的
- 导入的值允许修改

```js
var module = require("./a.js");
module.a;
// 这里其实就是包装了一层立即执行函数，这样就不会污染全局变量了，
// 重要的是 module 这里，module 是 Node 独有的一个变量
module.exports = {
  a: 1,
};
module.exports.a = 1;

// module 基本实现
var module = {
  id: "xxxx", // 我总得知道怎么去找到他吧
  exports: {}, // exports 就是个空对象
};

// 这个是为什么 exports 和 module.exports 用法相似的原因
var exports = module.exports;
var load = function (module) {
  // 导出的东西
  var a = 1;
  module.exports = a;
  return module.exports;
};
// 然后当 require 的时候去找到独特的
// id，然后将要使用的东西用立即执行函数包装下，over
```

## AMD 和 CMD

鉴于目前这两种实现方式已经很少见到，所以不再对具体特性细聊，只需要了解这两者是如何使用的以及区别。

**异步的 AMD** (Asynchronous Module Definition，异步模块定义) 和 require.js

- 采用异步方式加载模块，模块的加载不影响它后面语句的运行。主要用于浏览器端。
- 所有依赖这个模块的语句，都定义在一个回调函数中，等到加载完成之后，这个回调函数才会运行。
- require.js 是这个规范的典型实现
- require.js 用 `require.config()` 指定引用路径等，用 `define()` 定义模块，用 `require()` 加载模块。
- **依赖前置**：引用模块的时候，将模块名放在 `[]` 中作为 `reqiure()` 的第一参数；如果定义的模块本身也依赖其他模块，那就需要将它们放在 `[]` 中作为 `define()` 的第一参数。
- **提前执行**：加载前置依赖时就执行里面的代码。不过 RequireJS 从 2.0 开始，也改成可以延迟执行

**异步的 CMD**(Common Module Definition，通用模块定义) 和 Sea.js

- 和 AMD 一样，是浏览器端的异步模块加载方案，只不过在模块定义方式和执行时机上有所不同
- AMD 提倡依赖前置、提前执行，在定义模块的时候就要声明其依赖的模块
- CMD 提倡**就近依赖**（按需加载）、**延迟执行**，在用到某个模块的时候再去 require 进来。
- 玉伯开发的 sea.js 是典型实现，不过现在都已经废弃使用

```js
// AMD
define(["./a", "./b"], function (a, b) {
  // 加载模块完毕可以使用
  a.do();
  b.do();
});

// CMD
define(function (require, exports, module) {
  // 加载模块
  // 可以把 require 写在函数体的任意地方实现延迟加载
  var a = require("./a");
  a.doSomething();
});
```

## ES Module

ES Module 是 2015 年 ES6 原生实现的模块化方案，可以同时用于 Node 和浏览器，只是浏览器兼容性一直不好，不过 2021 基本也可以生产使用了，像 Vite 这样的工具都出来了。

### 设计思想

ES6 模块的设计思想是尽量的**静态化，使得编译时就能确定模块的依赖关系**，以及输入和输出的变量。这种加载称为“编译时加载”或者静态加载，即 ES6 可以在编译时就完成模块加载，效率要比 CommonJS 模块的加载方式高。

当然，这也导致了没法引用 ES6 模块本身，因为它不是对象，而是通过 export 命令**显式指定输出的代码**，再通过 import 命令输入。

import 命令会被 JavaScript 引擎**静态分析**，在编译时就引入模块代码，而不是在代码运行时加载，所以无法实现条件加载。【**静态结构特性，这也是 tree-shaking 能够去除死代码的原因所在**】

也正因为这个，使得静态分析成为可能。有了它，就能进一步拓宽 JavaScript 的语法，比如引入宏（macro）和类型检验（type system）这些只能靠静态分析实现的功能。

模块功能主要由两个命令构成：`export` 和 `import`。export 命令用于规定模块的对外接口，import 命令用于输入其他模块提供的功能。

还可以搭配 `as` 关键字。

```
// 引入模块 API
import XXX from './a.js'
import { XXX } from './a.js'

// 导出模块 API
export function a() {}
export default function() {}
```

### export

一个模块就是一个独立的 js 文件。该文件内部的所有变量，外部无法获取。

如果你希望外部能够读取模块内部的某个变量、函数（也是变量）或类，就必须使用 export 关键字输出它。

export 输出的变量就是本来的名字，但是可以使用 as 关键字重命名 `export { v1 as obj1}`

`export default` 命令，可以为模块指定默认输出。需要注意的是，这时 import 命令后面，不使用大括号。

本质上，export default 就是输出一个叫做 default 的变量或方法，然后系统允许你为它取任意名字。

```js
//modules.js
function add(x, y) {
  return x * y;
}
export { add as default };
// 等同于
//export default add;

//app.js
import { default as foo } from "modules";
// 等同于
//import foo from 'modules';
```

【注意】

1. export 命令规定的是对外的接口，必须与模块内部的变量建立一一对应关系，function 和 class 的输出也一样。

- `export function(){}`

1. export 语句输出的接口，与其对应的值是动态绑定关系，即通过该接口，可以取到模块内部实时的值。**【动态读取】？？？**
   这一点与 CommonJS 规范完全不同。**CommonJS 模块输出的是值的缓存（拷贝），不存在动态更新**。

```js
// 运行不是这样？
export var foo = "bar";
setTimeout(() => (foo = "baz"), 500); // 输出变量 foo，值为 bar，500 毫秒之后变成 baz
```

1. export 命令可以出现在模块顶层的任何位置。

- 如果处于块级作用域内，就会报错，import 命令也是如此。
- 这是因为处于条件代码块之中，就没法做静态优化了，违背了 ES6 模块的设计初衷。

### import

使用 export 命令定义了模块的对外接口以后，其他 JS 文件就可以通过 import 命令加载这个模块。

- import 命令接受一对大括号，里面指定要从其他模块导入的变量名。大括号里面的变量名，必须与被导入模块（profile.js）对外接口的名称相同。
- 如果想为输入的变量重新取一个名字，import 命令要使用 `as` 关键字，将输入的变量重命名。
- 除了指定加载某个输出值，还可以使用整体加载，即用星号（\*）指定一个对象，所有输出值都加载在这个对象上面。

注意，模块整体加载所在的那个对象上（例中是 profile），应该是可以静态分析的，所以不允许运行时改变。**【只读导入】**

```
import * as profile from './profile';
// 导入所有作为一个 profile 对象

// 下面两行都是不允许的
profile.foo = 'hello';
profile.area = function () {};
```

【注意】

1. import 命令导入的变量都是只读的，因为它的本质是输入接口，相当于 const xxx = yyy。也就是说，不允许在加载模块的脚本里面，改写接口。

- 实际上，如果导入的**命名导出是个对象**，是可以**改变**它的属性，并且其他模块也可以读到改写后的值。【但不能增删属性，只能改写已有属性】
- 不过，这种写法很难查错，建议凡是输入的变量，都当作完全只读，不要轻易改变它的属性。

```
import {a} from './xxx.js'
a = {}; 		// Syntax Error : 'a' is read-only; a 只是一个只读的接口

a.foo = 'hello'; // 合法操作，a 是一个对象，改写 a 的属性是允许的，但不推荐
```

1. import 命令同样可以出现在模块顶层的任何位置，且 import 命令具有提升效果，只要在顶层就可以提升到头部
2. import 后面的 from 指定模块文件的位置，可以是相对路径，也可以是绝对路径，.js 后缀可以省略。
   如果只有模块名，不带有路径，那么必须有配置文件，告诉 JavaScript 引擎该模块的位置。
3. 由于 import 是静态（编译时）执行，所以不能使用表达式、变量、流控制语句等只有在运行时才能得到结果的语法结构
4. import 语句是 单例 模式。import 语句会执行所加载的模块，但不可重复执行。因此可以有下面的写法。

```
import 'lodash';  // 仅仅执行 lodash 模块，但是不输入任何值

import 'lodash';  // 多次重复 import 同一句 import 语句，也只会执行一次。
import 'lodash';

// ---

import {foo} from 'my_module';
import { bar } from 'my_module';
// 等价于
import { foo, bar } from 'my_module';
```

### **export 、import 的复合写法**

如果在一个模块之中，先输入后输出同一个模块，import 语句可以与 export 语句写在一起。

但需要注意的是，写成一行以后，foo 和 bar 实际上并没有被导入当前模块，只是相当于对外转发了这两个接口，导致当前模块不能直接使用 foo 和 bar。

```
export {foo, bar} from 'my_module';
// 可以简单理解为
import { foo, bar } from 'my_module';
export { foo, bar };


// 接口改名
export {foo as myFoo} from 'my_module';
// 整体输出
export * from 'my_module';


export {es6 as default} from './someModule';
// 等同于
import { es6 } from './someModule';
export default es6;
```

### 严格模式

ES6 的模块自动采用严格模式，不管你有没有在模块头部加上 "use strict";。

严格模式主要有以下限制。

- 变量必须声明后再使用
- 函数的参数不能有同名属性，否则报错
- 不能使用 with 语句
- 不能对只读属性赋值，否则报错
- 不能使用前缀 0 表示八进制数，否则报错
- 不能删除不可删除的属性，否则报错
- 不能删除变量 delete prop，会报错，只能删除属性 delete global[prop]
- eval 不会在它的外层作用域引入变量
- eval 和 arguments 不能被重新赋值
- arguments 不会自动反映函数参数的变化
- 不能使用 arguments.callee
- 不能使用 arguments.caller
- 禁止 this 指向全局对象
- 不能使用 fn.caller 和 fn.arguments 获取函数调用的堆栈
- 增加了保留字（比如 protected、static 和 interface）

其中，尤其需要注意 `this` 的限制。

ES6 模块之中，顶层的 this 指向 `undefined` ，所以不要在顶层代码使用 this。

### 与 CommonJS 的区别

- CommonJS 是同步导入，因为用于服务端，文件都在本地，同步导入即使卡住主线程影响也不大。而后者是异步导入，因为用于浏览器，需要下载文件，如果也采用同步导入会对渲染有很大影响
- Commonjs 是运行时加载, ESM 是编译时加载
- CommonJS 模块就是对象；即在输入时是先加载整个模块，生成一个对象，然后再从这个对象上面读取方法
- ESM 不是对象，而是通过 export 命令显式指定输出的代码，import 时采用静态命令的形式。所以在 import 时可以指定加载某个输出值，而不是加载整个模块
- CommonJS 支持动态导入，也就是 `require(${path}/xx.js)`，后者是目前不支持，但是已有提案
- **⭐\*\***CommonJS 模块输出的是值的拷贝，ES6 模块输出的是值的引用\*\*
- **CommonJS 模块输出的是值的缓存（拷贝），不存在动态更新**。
- 如果导出基本类型，作为值的复制，导入后当然不会共享
- 如果导出引用类型，作为引用值的复制，导入后是可以共享变化的
- **导入的值允许修改**
- commonjs 模块执行时允许使用缓存
- 检查是否有该模块的缓存
- 如果有，则使用缓存
- 如果没有，则执行该模块代码，并缓存

```
// commonA.js
let r = {a:1}
module.exports = r;
r.b = 2

// index.js
let r = require('./commonA.js')
console.log('r: ', r); // r:  { a: 1, b: 2 }

r.c = 3;
console.log('r: ', r); // r:  { a: 1, b: 2, c: 3 }
```

- ES Module 采用实时绑定的方式，导入导出的值都指向同一个内存地址
- 导出不像 module.exports 那样整体是个对象，ESM 的导出由代码显式指定
- 只读导入：模块导入时，会执行类似于 const xx =yy 的命令来引用导出。
- 因为 const 只读，导入不允许改变内存，就是说：基本类型不允许改变值、引用类型不允许重新赋值（但修改内部已有属性是可以的，只是不建议）
- ？动态读取：导入值会跟随导出值变化，并且不会缓存值，模块里面的变量绑定其所在的模块。
- ES Module 目前来说还是会编译成 `require/exports` 来执行的

## 模块打包工具

- webpack

webpack，本质上是一个现代 JavaScript 应用程序的静态模块打包器。它递归的构建一个依赖关系图，其中包含应用程序的每个模块，然后将这些模块打包成一个或多个 bundle.js。

webpack 支持 CommonJS，AMD，ES6 等规范，所以我们在代码中可以使用多种模块加载规范，而且通过 loader，它不仅可以处理 JavaScript，还可以处理像 css，图片等等的静态资源。

- rollup

Rollup 是一个 JavaScript 模块打包器，可以将小块代码编译成大块复杂的代码，例如 library 或应用程序。

相比于 Webpack, rollup 更专注于打包 JS，常用于库的开发而不是项目的开发。

- Vite / Snowpack

在浏览器支持 ES 模块之前，JavaScript 并没有提供的原生机制让开发者以模块化的方式进行开发。这也正是我们对 “打包” 这个概念熟悉的原因：使用工具抓取、处理并将我们的源码模块串联成可以在浏览器中运行的文件。

诸如 [webpack](https://webpack.js.org/)、[Rollup](https://rollupjs.org/) 和 [Parcel](https://parceljs.org/) 等工具，它们极大地改善了前端开发者的开发体验。但是构建大型应用时就会发现打包的很慢。

现代浏览器对 ESM 的支持越来越好，就可以利用原生的 Module 来代替这些打包工具了，避免开发中的打包过程，从而加快构建，Vite/Snowpack 就是为此而生的。
