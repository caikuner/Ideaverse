## 同源策略和跨域

同源策略是一种**浏览器自身**的安全策略。不同源的站点之间互相请求资源（主要是 JavaScript 代码的访问），浏览器会**拦截响应**，不向前端交付。这就叫跨域。

**1.什么算同源**

- 协议相同（http/https）
- 域名相同（子域名不算同源）
- 端口相同

**2.同源策略的目的**
跨域是为了阻止用户读取到另一个域名下的内容，防范 CSRF 攻击，参考 [[安全：前端常见的安全攻防]]。

**3.同源策略会限制哪些内容**
主要是 Javascript 代码，JS 可以灵活操作响应。

- AJAX 请求
- Cookie、LocalStorage、IndexedDB 等存储性内容
- DOM 节点

这三个标签一般认为是资源文件，**允许跨域加载**：

```html
<img src=XXX>
<link href=XXX>
<script src=XXX>
```

**4.失败的跨域请求到底发出去了没有?**

发了，服务端也能收到请求，甚至可能正常返回响应到浏览器了。只是浏览器认为这个响应可能不安全给拦截掉了。这也说明，跨域并不能完全阻止 CSRF，因为请求毕竟是发出去了。

**5.对开发的影响**
目前前后端分离开发的模式下，前后端常常被部署在不同的位置，这时前端访问后端就会出现跨域不能访问资源的情况。
当然如果前后端部署在一起，是不会跨域的。

## 解决跨域的方式

**CORS（跨域资源共享）**

- 服务器设置 Access-Control-Allow-Origin 等响应头
- 可以配置允许的请求方法、请求头、是否允许携带认证信息等
- 最常用的跨域解决方案

**代理服务器**

- 开发环境：webpack、vite 的 dev-server proxy
- 生产环境：Nginx 反向代理

JSONP

- 利用 `<script>` 标签不受同源策略限制的特点
- 只支持 GET 请求
- 需要服务器配合返回 JavaScript 代码

postMessage

- HTML5 标准中的 API
- 用于**不同窗口间**的跨域通信
- 可以在父子页面（iframe）或者多窗口间通信

WebSocket

- 建立在 TCP 之上的协议
- 不受同源策略限制
- 适合需要**实时通信**的场景

## 跨域资源共享（CORS）

所有浏览器都支持该功能，CORS 也已经成为主流的跨域解决方案。

需注意的是：由于同源策略的限制，所读取的 cookie 为跨域请求接口所在域的 cookie，而非当前页。

### 简单请求

三个条件：
- 使用简单请求方法：GET、POST、HEAD
- 使用简单请求头：Accept、Accept-Language、Content-Language、Content-Type
- Content-Type 只能是以下之一：【注意最常用的 application/json 不在此列】
	- application/x-www-form-urlencoded
	- multipart/form-data
	- text/plain

对于简单请求，后端只需要加一个响应头 `Access-Control-Allow-Origin` 就可以实现指定域名跨域。
- `Access-Control-Allow-Origin: *` 会允许所有域名
- 最好前后端约定好一个域名白名单，尽量不要设置为 `*`

```js
// server
app.post("/form", (req, res) => {
  res.header("Access-Control-Allow-Origin", "*"); // 只需要设置这个头
  res.json({ success: true });
});
```

### 非简单请求 (三个头)

不符合以上条件的请求就是复杂请求了。比如，
- 使用了非简单方法如 PUT；
- 简单 header 使用了不简单的值 `content-type:"application/json"`;
- 使用了非简单 header `'X-App-Version':"v0.1"` 。


工作流程：

1. 浏览器自动发送 OPTIONS 预检请求，自动包含以下请求头：
	- Origin：请求来源
	- Access-Control-Request-Method：实际请求使用的方法
	- Access-Control-Request-Headers：实际请求使用的请求头
2. 服务器响应**预检请求**，返回：
	- **Access-Control-Allow-Origin：允许的源**
	- **Access-Control-Allow-Methods：允许的方法**
	- **Access-Control-Allow-Headers：允许的请求头**
	- Access-Control-Max-Age：预检请求的缓存时间, 秒
		- 非必需，预检请求快取优化
		- 有效期内的对于同一个资源的请求，浏览器不需要重复发送预检请求
	- Access-Control-Expose-Headers：可暴露给前端的响应头
		- 非必需，允许前端存取该自定义头
3. 浏览器检查预检响应
	- 如果**预检通过，浏览器才会发送实际请求**：实际请求的 源、方法、请求头都在允许范围
	- 否则，不会发出请求

```js
// server
const VALID_ORIGIN = "a.com,b.com"

app.options("/form", (req, res) => {
  res.header("Access-Control-Allow-Origin", VALID_ORIGIN);
  res.header("Access-Control-Allow-Headers", "X-App-Version, content-type");
  res.header("Access-Control-Allow-Methods", "PATCH,PUT,GET,POST");
  
  // 以下非必需
  // 1h 内同一资源请求不需要预检：
  res.header("Access-Control-Max-Age", "3600");
  // 允许前端存取自定义头 X-App-Version，否则前端只能取到响应体，拿不到这个头：
  res.header("Access-Control-Expose-Headers", "X-App-Version");
  res.end();
});
```

### 解决 cookie 的限制

当请求是跨域的，并且是用 CORS 协议解决的话，浏览器为安全计，ajax 请求是不会自动带上 cookie 的。于是每一个请求在后端都会创建一个新的 session，这太糟糕了。

**那如何给前端 (CORS) 跨域请求带上 cookie？** 参考：[[浏览器：Cookie]]

1. 前端：带上 credentials 选项
	1. XHR:`xhr.withCredentials = true`
	2. fetch: 加上参数 `credentials: 'include'`
	3. axios: `axios.defaults.withCredentials = true`
2. 后端
	1. Response header 额外增加 `Access-Control-Allow-Credentials: true`
3. 必须指明具体 Access-Control-Allow-Origin，不能设置为 `*`

```js
// 前端
fetch("http://damain1/form", {
	// ...
	method：'patch',
	credentials: "include", // 携带cookie新增
})
.then((res) => res.json())
.then((res) => console.log(res));


// 后端：
const VALID_ORIGIN = "http://domian1"; // 必须设置具体来源

app.patch("/form", (req, res) => {
  // ...
  res.header("Access-Control-Allow-Credentials", true); // 加上 cookie
  res.json({ success: true });
});

// 预检
app.options("/form", (req, res) => {
  // ...
  res.header("Access-Control-Allow-Origin", VALID_ORIGIN); // 必须设置具体来源
  res.header("Access-Control-Allow-Credentials", true); // 新增信任头
  res.end();
});
```

### 误区

错误示例：我们使用 fetch 时会认为 `mode: 'no-cors'` 参数可以有跨域的效果。
实际这个参数的意思只是：知道这个请求不能跨域，但是不要给我报错、也不要给我响应，所以结果就是 res 正常打印，但是里面 status=0，且没有实际响应数据。

```js
fetch("http://domain1.com/form", {
  mode: "no-cors",
}).then((res) => console.log(res)); // 有res，但里面的响应数据还是被浏览器拦截掉了
```

## 代理服务器

### 开发环境：webpack devserver proxy

在 webpack/vite 的开发环境中，本地会启动一个 node 服务 C ，代理客户端 A 所有对服务端 B 的请求。

- 本地 A-C 是同源的，可以正常请求
- 同源策略是浏览器的安全策略，node 服务不受限制，因此 C-B 可以正常请求

```js
// webpack.config.js
module.exports = {
  devServer: {
    proxy: {
      "/api": {
        // 匹配所有以 `/api` 开头的请求
        target: "http://www.domain2.com", // 目标服务器
        changeOrigin: true, // 修改请求头中的 Host（避免后端限制）
        pathRewrite: {
          "^/api": "", // 去掉 `/api` 前缀（可选）
        },
      },
    },
  },
};
```

```js
// vite.config.js
import { defineConfig } from "vite";

export default defineConfig({
  server: {
    proxy: {
      "/api": {
        target: "http://www.domain2.com",
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ""), // 去掉 `/api` 前缀
      },
    },
  },
});
```

### 生产环境：Nginx 反向代理

反向代理（reverse proxy）：是服务器的代理。在客户端 A 和真实服务器 B 之间，代理服务器 C 接受客户端连接请求，然后将请求转发给内部网络上的服务器，并拿到结果返回。

同样的，
- A-C 就是同一个域名，可以正常请求
- 同源策略是浏览器的安全策略，Nginx 服务不受限制，因此 C-B 可以正常请求

```nginx
server {
	listen 8081;
	server_name www.domain1.com;
	location /api {
		proxy_pass http://www.domain2.com:8080; #反向代理这个真正的目标服务
		proxy_cookie_domain www.domain2.com www.domain1.com; #修改cookie域名
		index index.html index.htm;

		add_header Access-Control-Allow-Origin http://www.domain1.com;
		add_header Access-Control-Allow-Credentials true;
	}
	location / {
		# 前端页面
	}
}

```

## WebSocket 代替 HTTP

WebSocket protocol 是 HTML5 规范的一种新的协议。它建立在 TCP 之上，实现了浏览器与服务器全双工通信，同时不受同源策略限制，允许跨域通讯。

## jsonp

- 浏览器允许 script 标签从不同域名下加载静态资源。再次可以请求一个带参网址实现跨域通信
- 只可以 get 请求

```html
<script>
  var script = document.createElement("script");
  script.type = "text/javascript";

  // 传参一个回调函数名给后端，方便后端返回时执行这个在前端定义的回调函数
  script.src = "http://www.domain2.com:8080/login?user=admin&callback=handleCallback";
  document.head.appendChild(script);

  // 回调执行函数
  function handleCallback(res) {
    alert(JSON.stringify(res));
  }
</script>
```

## postMessage

 postMessage 是 HTML5 XMLHttpRequest Level 2 中的 API，且是为数不多可以跨域操作的 window 属性之一。

 这种方式通常用于获取嵌入页面中的第三方页面数据。一个页面发送消息，另一个页面判断来源并接收消息。

postMessage (data,origin) 方法接受两个参数：
	- data： html5 规范支持任意基本类型或可复制的对象，但部分浏览器只支持字符串，所以传参时最好用 JSON.stringify () 序列化。
	- origin： 协议 + 主机 + 端口号，也可以设置为 "\*"，表示可以传递给任意窗口，如果要指定和当前窗口同源的话设置为 "/"。

```js
// 发送消息端
window.parent.postMessage('message', 'http://test.com')


// 接收消息端
var mc = new MessageChannel()
mc.addEventListener('message', event => {
  var origin = event.origin || event.originalEvent.origin
  if (origin === 'http://test.com') {
    console.log('验证通过')
  }
})
```
