### 1. 介绍项目

京东即时零售项目，聚焦本地即时消费场景，连接线下门店与线上用户，实现商品 30 分钟 - 1 小时送达。通过整合门店库存、物流调度系统，构建线上购物平台（含 App、小程序等端），用户下单后，系统智能分配订单给附近门店及骑手，保障履约效率，覆盖生鲜、商超、美妆、数码配件等多品类，满足消费者即时购物需求，提升本地零售数字化服务能力 。

### 2. 技术挑战难点是啥？没感觉到你说的难

- **订单履约链路复杂**：需协同门店拣货、骑手配送，涉及多系统（库存系统、订单系统、物流调度系统）实时交互，任何环节延迟或故障都影响履约，如库存扣减与实际拣货商品差异，需保障数据一致性与流程韧性。
- **多端兼容性**：覆盖 App、小程序、H5 等，不同端系统特性、性能表现不同，要适配机型、网络环境差异，保障页面加载速度、交互流畅度，比如小程序存在包大小限制、API 能力差异，需做针对性优化。
- **高并发场景**：促销活动（如本地生活节、大促联动）或高峰时段，订单请求瞬时激增，需保障系统吞吐量、响应速度，避免服务雪崩，要做好限流、降级、缓存策略及服务集群弹性扩容。

### 3. react 状态机制是啥？

React 状态机制核心围绕 `state` 与 `setState`（类组件）、`useState`（函数组件）展开：

- **类组件**：`state` 是组件内部可变数据存储容器，`setState` 用于更新状态，且是异步批量更新（为优化性能，合并多个状态更新操作），更新后触发组件重新渲染，如 `this.setState({ count: this.state.count + 1 })` 。
- **函数组件**：通过 `useState` 钩子声明状态，返回状态值与更新函数，更新函数是直接替换式更新（非合并），同样触发组件重新渲染，如 `const [count, setCount] = useState(0)` ，调用 `setCount(1)` 会替换 `count` 状态。此外，还有 `useReducer` 用于复杂状态逻辑管理，通过 reducer 函数处理状态变更，类似 Redux 模式 。

### 4. 有看过 react 源码嘛？

了解过 React 源码核心流程，比如：

- **调度流程**：基于 `requestIdleCallback` 思想实现的调度器（Scheduler），区分任务优先级，优先处理用户交互类高优先级任务（如点击事件触发的状态更新），延后处理低优先级渲染任务，避免阻塞浏览器主线程，保障页面响应流畅。
- **渲染流程**： Fiber 架构下，将虚拟 DOM 渲染拆分为可中断的“纤维”（Fiber 节点），遍历、对比、更新 Fiber 树，实现增量渲染，让复杂组件渲染过程更可控，配合调度器实现异步可中断更新 。不过未深入到逐行精读所有模块，更多聚焦关键流程原理辅助业务开发优化。

### 5. 看过什么的源码？

- **Vue 部分源码**：比如响应式原理模块，了解 `Object.defineProperty`（Vue2）或 `Proxy`（Vue3）实现数据劫持，收集依赖、触发更新的流程；还有模板编译部分，看如何将模板字符串转换为渲染函数。
- **Webpack 插件/Loader 源码**：为自定义构建流程，研究过简单 Loader（如处理特定格式文件转换）、插件（如实现资源打包后自动上传 CDN 逻辑）的源码结构，学习 Tapable 插件架构、 Loader 执行机制 。
- **axios 源码**：了解其封装 XMLHttpRequest（浏览器端）、http（Node 端）实现 HTTP 请求，以及拦截器、请求取消等功能的原理，辅助日常接口请求封装与异常处理优化 。

### 6. 源码里哪块涉及到了设计模式具体说一下

以 React 源码为例：

- **发布 - 订阅模式**：在事件系统中，组件挂载时会向事件调度中心订阅事件（如点击、输入事件），触发事件时发布通知，执行对应的事件处理函数，解耦事件触发与响应逻辑，方便扩展与维护。
- **代理模式**：Fiber 架构中，Fiber 节点可视为虚拟 DOM 节点的“代理”，在渲染流程中，通过操作 Fiber 节点（如标记更新、对比差异）代替直接操作真实 DOM，减少真实 DOM 操作开销，且能实现异步渲染、优先级调度等复杂逻辑，起到控制访问（真实 DOM）、增强功能的作用 。
- **单例模式**：React 的调度器（Scheduler）、全局的事件系统等，在应用中通常是单例存在，保障全局统一的任务调度、事件管理逻辑，避免重复初始化资源，比如整个应用只有一个调度器实例协调任务优先级与执行时机 。

### 7. 具体说一下你日常工作用过的设计模式，具体到功能

- **工厂模式**：在组件创建场景，如搭建多类型弹窗组件（确认弹窗、提示弹窗、带表单弹窗），用工厂函数根据配置参数（`type`、`content` 等），动态创建并返回对应弹窗组件实例，统一创建逻辑，方便扩展新弹窗类型，如：

```jsx
function PopupFactory(type, content) {
  switch (type) {
    case "confirm":
      return <ConfirmPopup content={content} />;
    case "tips":
      return <TipsPopup content={content} />;
    // 其他类型…
    default:
      return null;
  }
}
// 使用：const popup = PopupFactory('confirm', '确定删除？');
```

- **观察者模式**：在业务数据监听场景，如订单状态实时更新，订单模块作为被观察对象，其他关注订单状态的组件（如订单列表、履约进度组件）作为观察者订阅状态，订单状态变化时通知观察者更新视图，基于 `EventEmitter` 或自定义订阅 - 发布逻辑实现，解耦状态变更与视图更新逻辑 。
- **装饰器模式**：在函数组件性能优化中，用装饰器封装组件，添加日志打印、性能埋点、权限校验逻辑，比如给需要登录校验的页面组件加装饰器：

```js
function withAuth(Component) {
  return (props) => {
    const isLogin = checkLogin(); // 校验登录逻辑
    if (!isLogin) return <LoginPage />;
    return <Component {…props} />;
  };
}
// 使用：const AuthHome = withAuth(HomePage);
```

### 8. 你的日常写代码累计的开发经验说一下，怎么样降低错误出现

- **规范先行**：遵循团队 ESLint、Prettier 规则，统一代码风格；用 TypeScript 约束类型，减少类型不匹配错误，比如接口请求参数、返回值定义明确类型，避免传参、取值时类型混乱。
- **分层解耦**：拆分组件（UI 组件、业务组件、工具组件）、模块（网络请求模块、工具函数模块），单一职责原则，降低代码耦合度，比如网络请求统一封装，便于拦截器统一处理错误、加请求头，一处修改多处复用。
- **测试覆盖**：关键逻辑（如工具函数、业务流程函数）写单元测试（Jest、React Testing Library 等），保障功能正确性；复杂页面做 E2E 测试（Cypress 等），模拟用户操作流程，提前发现交互、逻辑错误。
- **日志与监控**：在关键节点（如接口请求开始/结束、重要状态变更）打印日志，方便调试；接入前端监控系统（如 Sentry），捕获运行时错误、性能异常，及时预警修复 。

### 9. react 有哪些组件？普通函数组件和高阶组件的区别是啥

- **React 组件分类**：
  - 按定义方式：**函数组件**（纯函数形式，接收 `props` 返回 JSX，简洁 lightweight ）、**类组件**（通过 `class` 定义，继承 `React.Component`，含生命周期等，渐趋少用 ）。
  - 按功能职责：**UI 组件**（专注展示，接收 `props` 渲染视图，无自身状态，如按钮、卡片组件 ）、**容器组件**（处理逻辑、数据，管理状态，渲染 UI 组件，实现逻辑与视图分离 ）；**高阶组件（HOC）**（接收组件返回新组件，用于逻辑复用，如权限校验、日志埋点组件 ）。
- **普通函数组件 vs 高阶组件**：

  | 对比项   | 普通函数组件                              | 高阶组件（HOC）                                                                |
  | -------- | ----------------------------------------- | ------------------------------------------------------------------------------ |
  | 定义形式 | 纯函数，`const Comp = (props) => <JSX />` | 函数，接收组件返回新组件，`const HOC = (Comp) => (props) => <Comp {…props} />` |
  | 核心作用 | 渲染 UI、处理简单交互逻辑                 | 复用组件逻辑（如权限、数据注入）                                               |
  | 状态管理 | 自身可通过 `useState` 等管理状态          | 一般管理公共逻辑状态，注入给被包裹组件                                         |
  | 调用方式 | 直接渲染 `<Comp />`                       | 包裹组件使用 `<HOC(Comp) />` 或装饰器形式                                      |

### 10. vue 和 react diff 上有什么区别

- **对比粒度**：
  - **Vue**：Vue2 中 `diff` 是全量对比（虚拟 DOM 树整体对比），Vue3 引入静态标记，对静态节点跳过对比，只更新动态节点；React 基于 Fiber 架构，按 Fiber 节点（细粒度“虚拟 DOM 片段” ）逐节点对比，可中断、恢复，更灵活控制渲染过程。
- **对比顺序**：
  - **Vue**：深度优先遍历虚拟 DOM 树，逐层对比节点；**React**：同样深度优先，但结合调度器，按任务优先级决定对比节奏，高优先级任务（如用户交互）优先对比、渲染，低优先级任务可暂停、延后。
- **更新策略**：
  - **Vue**：自动追踪响应式数据依赖，精准触发组件更新，`diff` 主要处理节点差异；**React**：通过 `setState` 触发更新，默认全组件树标记更新（可通过 `memo`、`PureComponent` 优化），`diff` 负责找出真正变化的节点渲染 。

### 11. 你们监控是怎么做的？

- **错误监控**：接入 Sentry，通过 `Sentry.init` 初始化 SDK，捕获 JavaScript 运行时错误（如语法错误、未定义变量调用）、React 组件异常（结合 `ErrorBoundary` 上报），配置错误采样、环境区分，及时通知开发人员。
- **性能监控**：用 `Performance API` 采集页面加载指标（首屏时间、白屏时间、资源加载耗时），结合 `Web Vitals`（如 LCP、FID、CLS ）上报，接入 APM 系统（如京东内部监控平台或第三方），分析性能瓶颈。
- **用户行为监控**：通过自定义埋点（如点击事件、页面跳转时调用上报函数）、自动埋点工具（如基于路由变化上报页面访问），记录用户操作路径、功能使用频率，用于分析业务流程、优化体验，数据汇总到数据分析平台做可视化展示与分析 。

### 12. 有没有根据业务数据做过相关优化？具体场景说一下？

**场景**：京东即时零售小程序首页，用户访问时加载慢、部分模块点击率低。

- **分析数据**：通过监控平台看性能数据（首屏加载耗时 3s+ ）、埋点数据（“为你推荐”模块点击率仅 5% ，远低于其他模块 ）。
- **优化动作**：
  - **性能优化**：拆解首屏请求，将非关键数据（如运营活动 banner ）改为懒加载；利用小程序缓存策略，缓存高频访问的商品分类、门店信息接口数据，首屏耗时优化至 1.5s 内。
  - **模块优化**：结合用户行为数据（地域、时段购买偏好），重构“为你推荐”算法，个性化推荐本地热门、应季商品，点击率提升至 18% ，带动下单转化 。

### 13. 业务 dau 是多少？业务反馈率是多少？

因实际业务数据属于公司内部机密且动态变化，无法提供准确值。通用思路：

- **DAU（日活跃用户数）**：可通过埋点统计小程序、App 等端的日登录、访问用户数，结合业务阶段（如推广期、稳定期）波动，推广期可能通过营销活动快速提升，稳定期注重留存与活跃。
- **业务反馈率**：一般指用户反馈（投诉、建议、问题上报）数 / 活跃用户数，通过客服系统、反馈入口收集数据，计算比例，用于衡量用户满意度与产品问题暴露情况，通常需控制在合理范围（如 1% - 5% ，依业务性质调整 ），并跟踪反馈处理率、解决率 。

### 14. 怎么处理用户反馈，快速定位问题的

- **流程**：
  1. **收集归类**：客服系统汇总反馈（如订单未履约、页面报错、功能异常），按类型（功能问题、体验问题、 Bug ）、业务模块（生鲜、商超等）分类。
  2. **技术定位**：
     - 结合用户提供的信息（操作路径、设备型号、系统版本、报错截图/文案 ），查询前端监控日志（Sentry 错误栈、性能日志 ）、后端接口日志，定位代码报错位置、接口调用异常。
     - 若涉及多端（如小程序 + 后端 + 物流系统 ），通过唯一订单号、请求 ID 串联各系统日志，排查链路问题（如订单分配给门店失败，查订单系统 - 门店系统交互日志 ）。
  3. **复现验证**：在测试环境模拟用户操作（设备、网络、流程），复现问题确认根因，制定修复方案，验证后灰度发布或全量上线，同步反馈用户处理结果 。

### 15. sass 是啥？

Sass（Syntactically Awesome Style Sheets ）是 CSS 预处理器，扩展 CSS 功能：

- **语法特性**：支持变量（`$color: #ff0;` ）、嵌套（`nav { li { color: red; } }` ）、混合（`@mixin` ，复用样式片段 ）、继承（`@extend` ，继承选择器样式 ）、条件判断（`@if` ）、循环（`@for` ）等，让样式编写更高效、可维护。
- **编译输出**：编写的 `.sass`（缩进语法）或 `.scss`（类 CSS 语法，更常用 ）文件，需通过编译器（如 `node-sass`、`dart-sass` ）转换为普通 CSS 文件，供浏览器识别，广泛用于前端工程化项目，提升样式开发效率与代码复用性 。

### 16. 有跨端经验么

有跨端开发经验，主要基于：

- **Taro**：用 React 语法开发多端应用（微信/京东/支付宝小程序、H5、App ），通过 Taro 编译工具转换为各端适配代码，统一业务逻辑开发，适配不同端 API 差异（如小程序的 `wx.request`、H5 的 `fetch` ，Taro 封装为统一请求方法 ）。
- **UniApp**：基于 Vue 生态，一套代码发布到多端，在即时零售营销活动页开发中使用，利用其组件库、API 跨端能力，快速覆盖多平台推广需求，处理过端适配问题（如小程序导航栏与 H5 导航逻辑差异 ）。
- **RN（React Native）**：参与过 App 部分模块开发，用 React 语法写原生组件（如商品列表、订单详情页 ），通过桥接原生能力（如相机、定位 ），实现跨 Android、iOS 端开发，处理过原生模块联调、性能优化（列表长列表渲染 ）问题 。

### 17. 小程序启动优化有哪些？有哪些框架？

- **启动优化手段**：
  - **代码包优化**：分包加载（将小程序拆分为主包 + 分包，首屏加载主包，其他包按需加载 ）；删除冗余代码、压缩资源（图片、JS 代码压缩 ），减小代码包体积。
  - **数据预加载**：提前请求首屏所需数据（如通过 `App.onLaunch` 预请求热门商品、门店信息 ），缓存到本地，减少首屏渲染等待时间。
  - **渲染优化**：简化首屏组件层级，避免复杂计算逻辑阻塞渲染；使用骨架屏占位，提升用户感知体验；懒加载非首屏模块（如底部 Tab 页内容 ）。
- **相关框架**：
  - **Taro**：支持多端小程序开发，内置分包配置、性能优化方案（如组件懒加载 ），辅助小程序工程化开发。
  - **UniApp**：提供一套代码多端编译能力，有启动优化相关 API（如 `preloadPage` 预加载页面 ）、组件库优化首屏渲染。
  - **原生小程序框架**：微信/京东小程序官方框架，可通过官方性能优化文档（如微信小程序启动流程优化、代码包管理 ），手动配置分包、预加载等策略 。

### **18. 小程序最大文件大小是多少？**

不同平台的小程序对文件大小有限制，常见限制如下：

#### **微信小程序**

- **单个代码包限制**：主包 + 所有分包 ≤ **20MB**
  - 主包（入口包）≤ **2MB**
  - 单个分包 ≤ **2MB**
- **资源文件**（如图片、音频）：
  - 单个文件 ≤ **10MB**（超过需使用 CDN 或分包加载）

#### **支付宝小程序**

- 主包 ≤ **2MB**
- 分包 ≤ **4MB**
- 总包 ≤ **16MB**

#### **字节跳动（抖音）小程序**

- 主包 ≤ **2MB**
- 分包 ≤ **4MB**
- 总包 ≤ **16MB**

**优化建议**：

- 使用分包加载（减少主包体积）
- 图片压缩 + CDN 托管
- 动态加载代码（`require` 或 `import()`）

### **19. WebSocket 连接建立、丢包处理、延时优化**

#### **（1）WebSocket 连接建立**

1. **HTTP 握手**（Upgrade 请求）：

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
```

1. **服务端响应**（返回 101 状态码）：

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

1. **连接建立**，后续通过 **帧（Frame）** 通信（二进制或文本数据）。

#### **（2）丢包处理**

- **心跳机制**（Ping/Pong）：定期发送 Ping 帧检测连接存活。
- **重连机制**：断连后自动重试（如指数退避算法）。
- **ACK 确认**：关键数据可要求服务端确认（需业务层实现）。

#### **（3）延时优化**

- **二进制数据**：使用 `ArrayBuffer` 替代 JSON 减少序列化开销。
- **压缩**：启用 `permessage-deflate` 扩展压缩数据。
- **CDN 加速**：WebSocket 代理节点就近接入。
- **减少帧大小**：分片发送大数据（如视频流）。
