    - 是什么：
        - 反作弊有离线、流式、在线三个过滤拦截系统，该平台是所有过滤系统的策略配置入口。为我们部门所有业务方向的策略同学，提供策略相关的管理工作，包括配置托管、上线、调研、查阅参考等。
    - 业务背景：
        - 我们有统一的一整套配置文件，包括词表、维度、特征、策略、Judge。我们每个策略业务方向、每个服务都在维护一套各自的配置文件，最终统一放在在线服务的一个代码仓库里，之前策略所有同学去修改同一个代码仓库，走工程流水线把配置推到线上的
    - 解决的业务问题 2 个：
        - **业务问题 1：工程流水线繁琐且耗费人力、堵塞、很难看到策略的影响：
            - 生效策略走工程流水线，耗费工程人力，本来工程人力就特别少
            - 同一个代码仓库工程上线，流水线堵塞
            - 配置文件不好管理，不知道谁哪天做了什么修改，产生多少收益，会有什么风险
            - 综上，**需要一个平台统一管理和分发所有配置文件，策略同学平台化操作**
        - **业务问题 2：配置复用问题**
            - 其实每个业务方向的配置内容，有很多是可以复用的，因为可能就是在拦截同一批黑产的作弊，作弊特征相似。但是大家都用代码仓库管理，很难去发现这种关联性；即使发现，也很不方便去复用
            - 所以 **需要平台去拆解这些配置，发现关联、复用的可能性**

### 简历项目内容

#### 某策略全周期管理平台 (负责人)

- 策略托管：平台化管理策略、特征等配置，提供编辑、Diff、配置生成等功能。设计可后台配置化的策略模板，快速生成填写表单；使用 CodeMirror 生成文本 Diff 视图，用于配置评审；基于统一的特征表达，适配不同的过滤系统，封装成统一的配置文本生成工具
- 策略验证：封装调用 Flink API，进行服务的创建、启停、配置加载等，完成数据流回放，验证策略正确性。平台化支持了原本复杂的工程步骤，极大便利策略的快速验证
- 策略上线：基于代码空间的设计概念，隔离不同的代码修改，零风险修改线上策略; 为解决同一产品线的上线阻塞问题，设计了两步上线的机制，单独拆分耗时操作，上线排队从 2d 缩短到 3h
- 特征中心：为了支持特征在不同系统的复用，设计了动态词表机制，通过 Redis 读写特征结果，在不同系统之间流转使用，极大便利了活动、电商业务的拉黑加白场景，支撑了全局黑产库的平台建设

#### 一站式风控平台 (核心开发)

`React` `Ant Design` `Tailwind CSS` `Vite` `Go` `MySQL`

`2023.11 - 至今`


该系统致力于打造统一的反作弊风控平台，使百度内部各业务方能够一站式、低成本地接入反作弊服务。提供业务接入、策略规则包上线、业务联调测试、数据看板等模块功能，快速接入风控能力。

- 系统搭建：从零开始搭建系统前端框架，推动 Vite、Tailwind CSS 的落地使用，提高开发效率
- 权限校验：封装后端权限校验中间件，前端权限校验工具函数，实现动态权限菜单和页面权限拦截
- 模块设计：完成应用接入、规则包、联调测试、数据看板等模块的设计开发，跑通平台业务流程，全链路加快业务接入。新业务耗时平均从 4d 缩短到 0.5d
- 规则包：对接策略管理系统，设计规则包的概念，通过配置模板的形式，为新接业务快速生成策略配置
- 联调测试：针对业务方联调测试困难的问题，平台化支持快速构造日志请求、自动验证参数和返回结果，无需人工介入。封装日志参数支持自定义校验规则的组件
- 数据看板：支持查询 ClikHouse 日志结果，使用 ECharts 可视化展示作弊拦截信息，满足业务方数据披露需求。查询请求可能打满，封装请求并发器进行限流
- 性能优化：保持主包 300KB 以下。公共依赖单独拆包，进行长效缓存；路由组件动态导入；三方库细粒度导入，如文本高亮库 shiki，动态导入语言和主题包，减小体积 70%

`JavaScript` `CDN` `Playw`

`2024.06 - 2024.09`
