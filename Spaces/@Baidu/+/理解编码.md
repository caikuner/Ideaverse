## 一、什么是乱码？


乱码是指在文本或数据中出现无法正确显示或解析的字符。当文本或数据的编码方式与解析它的环境或工具不匹配时，就会出现乱码问题。

乱码通常发生在以下情况下：

1. **编码方式不匹配**：当文本或数据使用一种编码方式进行编码，而解析或显示它的环境或工具使用了不同的编码方式时，就会出现乱码。常见的编码方式包括UTF-8、GBK、ISO-8859-1(Latin1, MySQL 5.7默认字符集)等。
    
2. **缺失或损坏的字符映射**：某些字符可能在特定编码方式下没有对应的字符映射或出现了损坏的字符映射，导致解析时无法正确显示。
    
3. **数据传输错误**：在数据传输过程中，如果出现错误或损坏，可能会导致字符的丢失或变化，进而导致乱码问题。
    

## 二、为什么会有乱码问题？

归根结底是中文编码映射的问题，不同的编码方案相互之间转换出错导致。

### 2.1 编码的历史

#### 2.1.1 英语编码解决方案**ASCII**

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=91003e4df6be44a3a2afd7fec6330589&docGuid=WXzkJXXlpm34mD)

ASCII第一次以规范标准的类型发表是在1967年，最后一次更新则是在1986年，到目前为止共定义了128个字符 。

英语是由26个基本拉丁字母、阿拉伯数字和英式标点符号组成，因此用128个符号就足够了，但ASCII码对于其他一些复杂的语言，就力不从心了，比如：汉字大约将近10万个（日常使用汉字也有几千字）。

**一个字节**只能表示256种符号，肯定是不够的，就必须使用多个字节表达一个符号。为了正确显示中文字符，在1981年5月1日，由中国国家标准总局发布了《信息交换用汉字编码字符·基本集》，通常简称**GB**。

#### 2.1.2 GB编码

中国大陆几乎所有的中文系统和国际化的软件都支持 [**GB2312**](https://baike.baidu.com/item/%E4%BF%A1%E6%81%AF%E4%BA%A4%E6%8D%A2%E7%94%A8%E6%B1%89%E5%AD%97%E7%BC%96%E7%A0%81%E5%AD%97%E7%AC%A6%E9%9B%86/8074272?fr=ge_ala)。GB2312是简体中文常见的编码方式，**使用两个字节表示一个汉字**，所以最多可以表示2^8 x 2^8 = 65536 个符号。

GB2312标准共收录6763个汉字，同时收录了包括拉丁字母、希腊字母、日文平假名及片假名字母、俄语西里尔字母在内的682个字符。

GB2312基本满足了计算机处理简体汉字的需求，所收录的汉字覆盖了99.75%的使用频率，但对于罕见字和繁体字，GB2312就不能处理了。因此发明了后来的GBK和GB18030。


但很多像GB类的编码方式都有一个共同的问题，**允许计算机处理双语环境，即拉丁字母和本地语言，却无法同时支持多语言环境，即多种语言混合的情况**。

**Unicode**就是为了解决这个问题而诞生的方案。

#### 2.1.3 Unicode字符集

假如有一种编码，将世界上所有的符号都纳入其中。每一个符号都给予一个独一无二的编码，那么乱码问题就会消失。这就是Unicode(Universal Multiple-Octet Coded Character Set)，**一种所有符号的编码**。

Unicode伴随着通用字符集的标准而发展，目前最新的版本为2022年9月公布的15.0.0，已经收录超过13万个字符。Unicode涵盖的数据除了视觉上的字形、编码方式、标准的字符编码外，还包含了字符特性，如大小写字母。

比如：

![](https://rte.weiyun.baidu.com/wiki/attach/image/api/imageDownloadAddress?attachId=1f18e8dbae344da5967550ffa8159cd7&docGuid=WXzkJXXlpm34mD)

其中，`\u7231`，表示的就是「你」这个字符在unicode中所在的位置是 7231，也就是十进制的第 29233 个字符。

然而，**Unicode只是一个符号集**，不代表计算机里的编码，它只规定了符号的二进制代码，却没有规定这个二进制代码应该**如何存储**。

#### 2.1.4 UTF-8

UTF：Unicode Transformation Format，简称为UTF

直接使用Unicode字符集，会有一个问题：较小值的编码点一般使用频率较高，直接使用Unicode编码(每个字符三个字节)效率低下，大量浪费内存空间。

而UTF-8的特点是对不同范围的字符使用不同长度的编码，它可以使用1~4个字节表示一个符号，根据不同的符号而变化字节长度。

### 2.2 产生乱码

如上所讲，我们既有本国自己制定的GB编码标准，又有统一的UTF-8标准，除此之外，还有繁体的Big-5，日文的Shift-JIS，这些编码之间如果编解码所用方案不一致，就会产生乱码：

- `巡音ルカ` (GBK) -> `Ñ²Òô¥ë¥«` (Windows-1252)
    
- `巡音ルカ` (UTF-8) -> `å·¡éŸ³ãƒ«ã‚«` (Windows-1252)
    

- `我能吞下玻璃而不伤身体。` (GBK) -> `扂夔迒狟產薛奧祥夼旯极﹝` (Big5)
    
- `我能吞下玻璃而不伤身体。` (UTF-8) -> `鎴戣兘鍚炰笅鐜荤拑鑰屼笉浼よ韩浣撱` (GBK, `errors='ignore'`)
    
- `我能吞下玻璃而不伤身体。` (UTF-8) -> `賢銝餌銝隡方澈雿` (Big-5, `errors='ignore'`)
    

#### 2.3 那么「锟斤拷」和「烫烫烫」呢？

Unicode和老编码体系的转化过程中，肯定有一些字，用Unicode是没法表示的，Unicode官方用了一个占位符来表示这些文字，这就是：U+FFFD，它的UTF-8编码是0xEFBFBD

# EFBFBD用gbk解码即为

b'\xef\xbf\xbd\xef\xbf\xbd'.decode('gbk') # -> '锟斤拷'

所以，锟斤拷必然涉及到utf-8和gbk的转换问题

而「烫烫烫」则是debug模式下VC(visual c++)对内存的初始化操作。VC会把栈中新分配的内存初始化为0xcc，VC的字符集是GB2312，而该字符集的0xcc位置，就是烫了

b'\xcc\xcc'.decode('gbk')  # -> '烫'

## 三、编码冷知识

MySQL 5.7 默认字符集是Latin1(iso-8859-1)，所以很多使用这个版本客户端的时候中文会有异常，需要手动设置为utf8mb4。

在mysql中也有utf8，但是它支持三个字节，所以很多数据显示不出来，2005年新增utf8mb4(most byte 4)修复了这个问题。所以，在mysql中我们要使用utf8mb4。
